부록 9~12페이지: 질의응답용


1페이지
[0:00–0:10 / 10초]
안녕하세요. G075 김지원입니다. 과제 2로 개발한 밤의 증언은 사람과 AI가 개인 기억을 바탕으로 토론하고 투표하는 추리 게임입니다.


2페이지
[0:10–0:40 / 30초]
AI가 다른 참가자의 비공개 정보까지 알면 추리가 성립하지 않습니다. 또 누군가의 발언을 확인된 사실로 받아들이면 오류가 누적됩니다. 그래서 참가자별 관측과 판단을 분리하고, 허용된 기록을 검색한 뒤, 주장과 근거를 검증하도록 만들었습니다. 주요 task는 역할별 AI, MCP 기억 조회, RAG 검색, 제한 재시도, 운영 모니터링입니다. 승패와 행동 규칙은 서버 코드가 결정합니다.


3페이지
[0:40–1:15 / 35초]
실제 OpenAI로 실행했던 게임 화면입니다. 사람은 역할에 맞게 행동하고 AI에게 질문할 수 있습니다. AI는 자기 관측으로 답변하며 공개 가능한 인용만 표시합니다. 이후 자기 역할 소개나 가정문을 잘못 막던 검증을 문장 범위별로 보완했습니다. 공개 인용은 화자와 원문을 대조합니다. 다만 자유 문장 전체가 정확하다는 보장은 없고, 복잡한 표현의 오차단과 누락은 남아 있습니다.


4페이지
[1:15–2:00 / 45초]
최신 비교는 구현 중 보지 않은 합성 문장을 코드 동결 뒤 확인한 평가입니다. 생성된 24개 중 조건을 어긴 2개는 제외 이유를 남겨 22개를 비교했습니다. 올바른 판정은 10개에서 18개, 근거 없는 단정을 놓친 경우는 9개에서 1개로 바뀌었습니다. 하지만 정상 발언 오차단은 3개로 그대로입니다. 더 많이 잡으면서 단정 수정 재시도는 2회에서 10회로 늘었습니다. 같은 출력을 반복하는 평가여서 실제 모델의 성공률이나 비용 절감으로 해석하지 않습니다. 결과는 MLflow에서도 비교할 수 있습니다.


5페이지
[2:00–3:00 / 60초]
이제 decision.py의 Agent Graph 코드입니다. 기억 검색, 생성, 근거 검증, 재검색, 수정, 기본 행동 노드를 연결합니다. 그래프는 한 번 컴파일하고, 현재 참가자의 관측과 실행 상태는 매 판단 분리합니다. 생성 단계는 JSON 형식과 인용 ID를 검사합니다. 검증 단계는 구조화된 주장이 관측으로 뒷받침되는지 확인하고, 일반 의견에 사실 단정이 숨어 있는지도 검사합니다. 관련 근거가 부족하면 research로 돌아가고, 문장 수정이 필요하면 repair를 거칩니다. 생성은 최대 3회, 재검색은 최대 2회입니다. 해결하지 못하면 기권이나 기본 행동으로 종료합니다. 참가자별 논리적 에이전트가 같은 그래프와 통신 자원을 공유하므로 참가자 수만큼 모델 서버를 만들지는 않습니다.


6페이지
[3:00–3:45 / 45초]
MCP는 서비스 시작 시 stdio 연결을 만들고 재사용합니다. 이 코드에서 현재 참가자가 볼 수 있는 관측만 서명해 register_context에 등록합니다. 검색은 임시 capability로 호출하고, 완료 후 finally에서 release_context로 정리합니다. 따라서 다른 참가자 ID를 넣어 개인 기억을 조회하는 도구가 아닙니다. 규칙 문서는 Resource, 계속 변하는 기억 조회는 Tool로 나눴습니다. 서버 종료와 검색이 겹치는 실패 경로도 테스트했습니다.


7페이지
[3:45–4:30 / 45초]
RAG는 참가자 기록을 검색해 모델 입력에 넣습니다. 이 expanded_terms 코드가 기본 어휘에 게임의 동의어와 관련 개념을 더합니다. 예를 들어 목격과 마주침, 보호와 치료 같은 표현을 연결합니다. 검색 관계가 곧 사실의 동일함을 뜻하지는 않습니다. 상위 기록에 최근 기록과 중요한 개인 조사 결과를 보존하고, 문맥 크기 예산을 적용합니다. 추가 임베딩 호출과 벡터 DB 없이 동작하지만, 사전에 없는 표현은 놓칠 수 있습니다. 현재 게임 규모에서는 이 한계를 측정하면서 유지하고, 의미 검색은 효과가 확인되면 추가하려고 합니다.


8페이지
[4:30–5:00 / 30초]
운영 화면에서 AI 판단뿐 아니라 규칙 적용과 DB 저장까지 확인합니다. Docker의 실제 게임에서 AI 행동 76건이 저장됐고, 7건은 기본 행동 대체였습니다. MLflow는 숫자를 비동기로 기록하며 장애 시 게임을 유지합니다. 가상환경과 Docker에서 각각 211개 테스트를 통과했습니다. 검증 강화는 수정 비용을 늘릴 수 있어, 기능 추가만큼 한계를 측정하는 과정이 중요했습니다.

예상 질문과 답변

Q. RAG인데 벡터 DB가 없나요?
A. 허용된 게임 기록을 검색해 생성 입력으로 제공하므로 RAG입니다. 어휘·게임 표현 확장 검색을 사용하며 임베딩과 벡터 DB는 사용하지 않았습니다. 의미 검색 도입과 별도 DB 운영도 다른 결정입니다.

Q. 18/22면 게임 추리 정확도가 81.8%인가요?
A. 아닙니다. 합성 고정 문장의 허용·차단 분류 결과입니다. 실제 승률이나 모델 전체 생성 품질이 아닙니다. 구현 에이전트가 문장을 검토했고, 외부 사람 검수와 대표 표본 확보는 남은 과제입니다.

Q. 정상 오차단도 개선되었나요?
A. 개발 중 확인한 자기소개·가정문 사례는 수정했지만, 코드 동결 뒤 본 22건에서는 3건으로 같았습니다. 복잡한 수식어, 불확실성 표현, 일부 인용 형식이 한계입니다.

Q. 검증을 강화하면 더 느리거나 비싸질 수 있나요?
A. 그렇습니다. 검증 자체는 추가 LLM 호출이 없지만, 잘못된 답을 더 많이 잡으면 수정 요청이 증가합니다. 이번 재생 평가에서도 단정 수정 시도는 2회에서 10회가 되었습니다. 비용 절감을 주장하지 않습니다.

Q. MLflow와 LangSmith는 어떻게 다른가요?
A. 이번 구현에서 LangSmith는 상세 Agent 추적, 운영 페이지는 현재 실행 단계와 자원 상태, MLflow는 숫자 지표와 실험 비교를 담당합니다. MLflow에도 별도 추적 기능이 있지만 이번에는 REST Run 지표 연동을 구현했습니다.

Q. Airflow도 썼나요?
A. 아니요. 요청한 AI 실행 흐름 화면을 구현했습니다. Apache Airflow는 정기 배치 평가의 예약·의존성 관리가 필요할 때 검토할 도구입니다.

Q. 화면에서 값이 0인 이유는 무엇인가요?
A. 운영 지표는 서버 시작 이후 수집합니다. 새 AI 판단이 없으면 0이고, 과거 게임 DB나 합성 테스트 수치를 섞지 않습니다. 합성 테스트는 별도 포트와 별도 MLflow 실험으로 검증했습니다.

Q. MLflow가 멈추면 게임도 멈추나요?
A. 전송은 별도 스레드와 최대 64개 큐에서 처리합니다. 실패·초과 시 숫자 기록을 누락하고 횟수를 표시하므로 게임 판단을 막지 않습니다. 대신 누락 샘플의 영구 재전송은 지원하지 않습니다.

Q. 비용과 메모리 값은 정확히 무엇인가요?
A. API가 반환한 입력·출력 토큰을 수집하며 청구 금액은 추정하지 않습니다. RSS는 게임 프로세스 최대 사용량이며 MLflow와 MCP 프로세스는 포함하지 않습니다.

발표 전 확인

3. 기본 발표는 1~8페이지, 부록은 9~12페이지
4. Docker 게임 8300 / 운영 8300/ops / MLflow 5600. 가상환경은 8200/5500으로 구분
5. 라이브 API가 지연되면 내장된 실행 캡처 사용. 운영 접근 키는 발표 전에 입력
6. .env, 참가자 비공개 기록은 화면 공유하지 않기
7. MLflow 비교는 왼쪽 개선 후·오른쪽 이전이며 Duration은 결과 등록 시간

Q. Docker를 쓰면 AI가 더 빨라지나요?
A. 이번 도입 목적은 환경 재현과 서비스 관리입니다. 게임·MCP와 MLflow를 함께 기동하고 데이터를 볼륨에 보관합니다. AI 속도 향상은 주장하지 않습니다. 개인 PC 실행용이며 인터넷 공개 배포와 여러 서버 확장은 별도 과제입니다.
