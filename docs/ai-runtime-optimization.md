# AI 실행 효율과 운영 보호

## 변경 사항

- 기록 토큰화만 방·참가자·이벤트 ID·내용 해시로 구분해 재사용한다. 답변, 전체 관측, 동적 검색 순위는 캐시하지 않는다. 수정된 기록은 새 키를 사용한다.
- 캐시는 프로세스별 최대 1,024개·추정 2 MiB, 마지막 접근 후 300초 만료, LRU 퇴출이다. 만료 정리는 다음 접근 시 수행한다. Python 객체 추정 크기 제한이지 서버 RAM 제한이 아니다. 직접 검색과 MCP 프로세스는 캐시가 별개다.
- 개인 판단은 기존 이벤트 접두부 해시가 일치하면 새 이벤트의 사실만 해석한다. 수정·삭제 시 다시 계산한다. 접두부 검증·관측 복사는 여전히 O(N)이며 전체 처리가 O(신규 이벤트 수)는 아니다. 체크포인트는 비공개 저장 상태에만 남긴다.
- 모델 입력의 반복 발언 원문을 이미 전달한 이벤트 ID로 참조하고, 동일한 판단 변화는 이력 인덱스로 참조한다. 검색된 증거 원문은 자르지 않는다. 운영 진단 정보는 입력에서 제거한다.
- 형식·내용 수정 재시도에 고정 대기를 넣지 않는다. 외부 모델 HTTP 408·429·5xx 및 연결 오류는 일시 오류로 분류해 지수 대기와 jitter를 적용한다. Retry-After는 최대 30초로 제한하며 기존 그래프 생성 횟수 제한을 유지한다. 그 외 HTTP 오류는 중단한다.
- 외부 모델 입력은 GAME_MAX_PROMPT_BYTES(기본 262144)로 제한한다. UTF-8 바이트 제한이며 토큰 제한이 아니다. 초과 시 근거를 임의로 버리지 않고 오류로 중단한다.
- MCP 대기열은 최대 16개이며 포화 시 실패를 알린다. 취소된 대기 작업은 실행하지 않는다.
- 감사 기록에 결정·대기·재시도 대기 시간, 관측/선택 이벤트 수, 검색 캐시 통계, 사실 해석량을 남긴다. 검색 통계는 마지막 검색의 값이며 여러 재검색의 합계가 아니다.

## 운영 확인

GET /health/live는 프로세스 응답 여부, GET /health/ready는 초기화 완료·로컬 MCP 종료 여부·SQLite SELECT 1 성공 여부를 확인한다. 준비되지 않으면 503이다. 키·방·발언은 반환하지 않는다. 외부 모델 API나 LangSmith의 정상 동작, MCP 왕복 성공을 보장하는 검사는 아니다.

모델 토큰 기준 예산과 운영 모니터링 대시보드는 아직 포함하지 않았다. 방 간 제한 병렬 실행은 아래 후속 개선에서 적용했다.

## 재현과 실측 한계

```sh
.venv/bin/python -m game.benchmark_runtime
.venv/bin/python -m unittest discover -s tests
node --test tests/map_motion.test.cjs
```

[집계 결과](../reports/runtime-optimization-v1.json)는 7명·약 180개 기록에서 25회 이벤트를 추가하는 오프라인 합성 실험이다. 전후 각각 새 프로세스에서 실행한다. before는 캐시·증분 갱신·입력 압축을 끈 동일 구현의 재계산 기준이며 과거 커밋 그대로가 아니다. tracemalloc 오버헤드가 포함되고, 반복 신뢰구간을 측정하지 않은 단일 실험이다. 실제 API 토큰·요금·답변 품질·전체 응답 지연은 측정하지 않았다.

검색 이벤트와 공개 판단 상태의 해시는 전후 일치한다. 캐시 적중은 4,668/4,875(95.8%)이며 프롬프트 바이트는 약 10.1% 줄었다. 사실 해석량은 감소했지만 이 작은 작업에서는 해시·복사·캐시 관리 비용으로 평균 시간이 약 5.1% 늘고 메모리도 늘었다. 따라서 속도나 RAM 절약에 성공했다고 주장하지 않는다. 실제 장기 게임에서 재측정하고 캐시 유지 여부를 결정해야 한다. 원문 보존과 프로그램 상태 일치는 모델의 참조 이해·답변 품질 동등성을 보장하지 않는다.

실습 연결: 01의 객체 재사용, 02의 변경 가능 정보 캐싱 경계, 09의 오류별 재시도, 10의 비용 측정 구분, 12의 상태 복구, 13의 테스트 가능한 의존성, 14의 실행 관측을 확장한다. 게임 결과나 참가자 개인 정보를 공유 캐시 키에서 생략하지 않는다.

## 저장 게임 재측정과 적용 결정

`python -m game.benchmark_saved_memory`로 로컬 종료 게임 4개·참가자 관측 26개에 서로 다른 검색어를 반복했다. 6회 전후 실행 순서를 교대했고 각 조건·회차당 130건을 실행했다. 종료 시점 관측 재검색이며 과거 턴 상태 재생이나 새 LLM 플레이가 아니다. 원문·방 ID는 보고서에 넣지 않는다.

[집계](../reports/saved-memory-cache-v1.json): 미사용 평균 1.206 ms, 캐시 사용 4.186 ms. 선택 이벤트는 모두 같지만 적중 0회, 마지막 실험 퇴출 18,812회였다. 참가자별 기록이 2 MiB 범위를 넘어 반복 교체되는 부하에서는 역효과다. 이에 토큰화 캐시는 기본 비활성화했다. GAME_MEMORY_TOKEN_CACHE=true로 실험할 수 있으며 MCP 하위 프로세스에도 전달한다. 증분 판단·프롬프트 정리는 유지한다.

## 종료 방 메모리 관리

시작할 때 종료 방을 복원하지 않는다. 회고 요청 시 SQLite에서 다시 읽으며 인증을 유지한다. 30초마다 마지막 접근 후 60초 이상 지난 종료 방을 저장 후 메모리에서 제거한다. 연결된 WebSocket, 진행 중 작업, 잠긴 방, busy 상태는 보호한다. WebSocket 종료 시 유휴 시간을 다시 계산한다. 진행·일시 정지·대기 방은 유지하며 생성 한도는 종료 방을 제외한 100개다. DB 기록은 삭제하지 않는다.

이 정리는 Hub의 참조를 해제한다. Python 할당자가 메모리를 보유할 수 있어 운영체제 RSS가 즉시 내려간다는 보장은 없다. 종료 방에 계속 접속한 사용자가 있거나 미완료 방이 많으면 메모리가 남는다. 단일 서버 프로세스용 설계를 유지한다.

## 연결 재사용·실행 제어·불필요한 호출 생략

서버 lifespan에서 HTTP 연결 풀 하나를 준비하고 종료 시 닫는다. 실제 TCP 연결은 요청 때 필요에 따라 생성한다. OpenAI/Gemini의 프로토콜은 기존 그대로이며 방별 모델 클라이언트·호출 예산·metrics는 별개다. 인증 헤더는 요청마다 전달하고 리디렉션은 따라가지 않는다. CLI의 기존 기본 전송 경로는 유지한다.

GAME_AI_CONCURRENCY(1~8, 기본 2)로 서로 다른 방의 판단 동시 실행 수를 제한한다. 방 내부는 기존 작업 하나와 순서를 유지한다. 대기자는 최대 16개, 슬롯 대기 제한은 30초다. 포화/대기 초과는 방을 일시 중지하고 재개 안내를 남긴다. 병렬성이 늘면 API 호출 제한에 빨리 도달할 수 있다. MCP 검색 자체는 기존 단일 처리이며 모델 호출 병렬화가 MCP 병렬화를 의미하지 않는다.

취소된 asyncio 작업의 동기 스레드는 즉시 멈추지 않는다. 따라서 시작된 판단 스레드가 끝날 때까지 실행 슬롯과 공통 자원을 유지하고 취소된 결과는 게임에 반영하지 않는다. 이 때문에 정상 종료가 늦어질 수 있다. 30초 제한은 대기열 시간이며 전체 판단의 강제 종료 제한은 아니다. 후속 개선에서 아래의 협력적 시간 예산과 장애 차단을 추가했다.

밤 행동의 모든 필드가 단 하나의 enum 값으로 고정된 경우에만 검색·모델 호출을 생략한다. 시민이어도 방문 장소 선택이 남아 있으면 모델을 호출한다. 자유 발언·투표는 생략하지 않는다. 생략은 실패 fallback이 아니며 attempts=0, forced_action 경로를 감사 기록에 남긴다. 이 턴에는 개인 판단을 갱신하지 않고 다음 실제 판단에서 누적 기록을 처리한다. model_calls_saved=1은 기본 생성 1회 생략을 의미하며 재시도·요금 절감 실측은 아니다.

추가 회귀 테스트는 동시 실행 상한, 대기열 포화/시간 초과, 취소 중 슬롯 보호, 공통 전송과 별도 방별 예산·지표, 오류 메시지 비밀 제거, 완전히 고정된 행동에만 호출 생략을 검증한다. 전체 126개 테스트 통과. 실제 외부 API 지연·비용이나 TCP 재연결 횟수는 이번에 측정하지 않았다.

## 판단 시간 예산·반복 장애·모델 라우팅

GAME_DECISION_SECONDS(기본 120초)는 실행 슬롯을 얻은 뒤 시작하는 협력적 시간 예산이다. 검색·생성·재시도 경계에서 확인하고 외부 API timeout 및 MCP 대기 시간을 남은 예산 이하로 제한한다. 완료 시에도 확인하여 기한이 지난 행동은 반영하지 않고 방을 일시 중지한다. ContextVar를 사용하므로 동시 실행 방의 예산이 섞이지 않는다.

이것은 스레드 강제 종료가 아니다. HTTP timeout은 개별 네트워크 동작 기준이며 이미 실행 중인 MCP 요청·로컬 모델·CPU 작업이 즉시 중단되지는 않는다. 종료가 지연될 수 있고 이미 보낸 API 요청의 과금도 취소되지 않는다. 취소·시간 초과는 이미 발생한 비용을 되돌리는 기능이 아니다.

서버 공통 외부 API 전송 계층은 엔드포인트별 연속 일시 오류 3회에 30초 차단한다. HTTP 408·429·5xx 및 연결 오류가 대상이며 인증/설정 오류나 생성 내용의 검증 실패는 장애 횟수에 넣지 않는다. 정상 응답은 연속 실패 횟수를 초기화한다. 차단 후 한 요청만 복구 확인을 하며, 그동안 다른 요청은 일시 중지된다. 실제 API 성공 응답을 검증 단계에서 거부한 경우에도 네트워크 장애로 세지 않는다. 차단은 서버 프로세스 범위이고 이미 진행 중인 호출은 취소하지 않는다. OpenAI의 공통 엔드포인트를 쓰는 모델들은 차단 상태도 공유하므로 한 모델의 장애가 다른 모델의 호출을 잠시 막을 수 있다.

선택 설정 GAME_FAST_MODEL은 밤/투표, GAME_QUALITY_MODEL은 토론/협의 및 재작성에 사용한다. 명칭이 실제 속도·품질 우위를 보장하지 않는다. 같은 제공자 안에서 명시적으로 선택하고 비우면 GAME_MODEL로 돌아간다. Ollama에는 이 라우팅을 적용하지 않는다. 모든 경로가 하나의 방별 호출 예산을 공유하고 실제 모델명과 model_route가 지표에 남는다. 사용자 .env는 수정하지 않아 기존 모델을 유지한다. 토론 품질이나 비용 절감은 별도 실모델 평가가 필요하다.

고정 회귀 테스트: 시간 예산 초과 결과 거부·ContextVar 복원, 차단 임계치·단일 복구 요청·인증 오류 제외, 라우팅과 통합 호출 예산을 검증한다. 실제 모델 비교 평가 세트와 제공자 장애 부하 실험을 대체하지 않는다.

## 운영 경로 재검토와 회귀 보완

정상 동작뿐 아니라 취소·시작 실패·복구 순서까지 검토했다. 아래 오류는 별도 회귀 테스트로 수정 전 실패를 확인한 뒤 수정했다.

| 경로 | 발견된 문제 | 보완 |
|---|---|---|
| 반복 취소 | 두 번째 취소가 동기 작업 대기를 취소해 슬롯이 먼저 반환됨 | 반복 취소에도 worker를 shield하며 완료까지 슬롯 유지 |
| 정상 종료 중 취소 | 마지막 호출 횟수·토큰 사용량이 저장되지 않음 | 작업 종료 후 사용량을 저장하고 방을 paused로 보존, 취소된 행동은 미반영 |
| 늦은 모델 응답 | 시간 예산 확인이 usage 추출보다 먼저라 사용량 누락 | 전달받은 usage를 먼저 기록하고 시간 초과 결과는 거부 |
| 클라이언트 재개 검사 실패 | 복원 전 check 실패 시 calls=0으로 덮임 | 저장된 호출 횟수를 먼저 복원한 뒤 설정 검사 |
| 부분 초기화 실패 | HTTP 풀 준비 실패 시 MCP, DB 초기화 실패 시 연결이 남음 | 획득한 자원만 정리하고 다른 정리 실패에도 후속 자원 해제 |
| 잘못된 운영 설정 | NaN 등 시간 설정이 첫 판단 때까지 검증되지 않음 | 자원을 열기 전 유한한 양수·동시성 범위 검증, 서버 수명 동안 같은 설정 사용 |
| MCP 종료/검색 경합 | 종료 sentinel 뒤에 요청이 추가되어 응답을 기다림 | 종료·등록을 같은 잠금으로 보호하고 취소된 Future 완료 경합 처리 |

MCP 생성 중 시작 취소도 별도로 검증했다. 생성 작업이 끝날 때까지 기다린 후 아직 인계되지 않은 자원을 닫는다. 정상 종료의 사용량 보존은 프로세스 강제 종료(SIGKILL)나 시스템 장애 때 마지막 메모리 상태까지 보장하지 않는다.

검증에는 두 방의 판단이 실제 서로 다른 스레드에서 겹쳐 실행되고 예산·사용량이 분리되는 통합 시나리오, 로컬 HTTP/1.1 서버의 같은 TCP 연결 재사용도 포함한다. 이는 실제 외부 제공자의 연결 재사용율·성능 실측은 아니다. 새 검토 테스트 11개를 추가했고, 최종 Python 141개·JavaScript 4개 테스트가 통과했다. 유료 모델 호출은 하지 않았다.

호출 한도는 네트워크 요청 건수나 청구 건수와 다르다. 회로 차단·입력 크기 거부처럼 요청을 보내기 전에 실패한 생성 시도도 한도에 포함한다. 응답에서 usage를 받지 못하면 토큰 수는 알 수 없음으로 유지하며 0으로 가정하지 않는다. 키·모델 설정은 사용자 .env를 유지한다.

## 문맥 예산과 정책 의존성

`RuntimeSettings.from_env()`에서 `ContextBudget`과 `SuspicionPolicy`를 생성·검증하고 lifespan 동안 재사용한다. 두 객체는 변경 불가능한 정책만 보유한다. 참가자의 검색 결과, 판단 기억, 예산 사용 내역은 매 판단마다 별도로 만든다. 방별 모델 클라이언트는 기존처럼 최초 AI 실행 때 생성한다. 설정 변경은 서버 재시작 후 적용된다.

- `GAME_CONTEXT_BYTES=32768`: 모델에 전달할 observation JSON의 UTF-8 바이트 상한. 허용 설정 범위는 1024~262144다. 전체 시스템 프롬프트·스키마·응답 토큰·방의 누적 비용 제한은 아니다.
- `GAME_SUSPICION_DAYS=2`: 의심 근거의 경과 일차 허용치. 0~30을 허용한다.
- 기존 `GAME_MAX_PROMPT_BYTES=262144` 전체 메시지 상한과 생성 시도 횟수 한도는 별도로 유지한다. 사용자 `.env`는 변경하지 않았으며 새 설정을 생략하면 위 기본값을 사용한다.

문맥 예산은 최초 검색 및 매 재검색 뒤, 토론 맥락과 개인 기억을 붙인 다음 적용한다. 검색 순위가 낮은 선택 기록부터 제외하고 순위가 없으면 오래된 기록부터 제외한다. 개별 이벤트 원문을 중간에서 자르지 않는다. 조사·검시·공격 목격·추적·시체 신고, 현재 늑대 협의, 현재 질문과 인용, 최근 토론 문맥 참조, 개인 판단 근거를 보존한다. 서버 원본 기록과 DB는 삭제하지 않는다.

필수 참조가 빠지거나 필수 근거와 메타데이터만으로 예산을 초과하면 모델 호출 전에 실패한다. 웹은 방을 일시 중지하고 안내하며 게임 행동을 적용하지 않는다. 필수 근거를 버리는 방식으로 자동 해결하지 않는다. 검색으로 이미 누락된 일반 기록을 예산 정책이 복구하는 것은 아니다. 원문·필수 근거 보존이 모든 추론 품질을 보장하지도 않는다.

감사 기록 `runtime.context_budget_history`에 검색 단계별 제한/전후 바이트/제외 기록 수를 남긴다. 검색 순위와 운영 통계는 모델 입력에서 제거한다. 크기 계산용 복사·직렬화·정렬 비용이 추가되며 서버 RSS 또는 전체 세션 메모리 상한을 구현한 것은 아니다. 토큰과 바이트는 서로 다르므로 API가 반환한 실제 토큰은 별도 기록한다.
